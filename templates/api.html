RegCheck API

HTTP API reference

RegCheck exposes a small HTTP API behind the same endpoints the web app uses. A comparison is submitted as a multipart/form-data request, runs asynchronously on a worker, and is then polled for status and results. This page documents the request fields, the polling response, and the report-artifact endpoints used to retrieve highlighted evidence.

No API key is required. RegCheck holds its own model-provider credentials server-side; you choose which provider processes your documents with the client field. Please review the Privacy Policy for how uploaded content and prompts are handled by each provider.

1) Base URL & flow

All paths are relative to the site origin (for example https://<your-regcheck-host>). A typical run has three steps:

  • Submit a comparison with POST /compare (or a comparison-type-specific endpoint). The response is a 302 redirect to /survey/<task_id> — the task_id is the final path segment of the Location header.
  • Poll GET /task_status/<task_id> until state is "SUCCESS" or "FAILURE".
  • Retrieve the rendered report at GET /result/<task_id> (HTML) or pull the structured result and evidence artifacts via the JSON/report endpoints below.

2) Submit a comparison

POST /compare

Content type: multipart/form-data. Use clinical_registration=yes with a registration_id for a ClinicalTrials.gov registration, or provide a preregistration file for a general preregistration comparison.

FieldRequiredDescription
clientyesModel provider: openai, groq, or deepseek.
parser_choiceyesPDF parser: grobid (typeset journal PDFs), dpt2 (less standard documents / OCR), or pymupdf (in-process; keeps all selectable text including author notes).
dimensions_datayesJSON array of the dimensions to compare (see below).
paperyesThe published paper file (.pdf or .docx).
preregistrationcond.The preregistration file (.pdf, .docx, or .txt). Required unless clinical_registration=yes.
clinical_registrationnoyes/no (default no). When yes, a ClinicalTrials.gov registration is fetched from registration_id.
registration_idcond.ClinicalTrials.gov identifier (e.g. NCT01234567). Required when clinical_registration=yes.
reasoning_effortnoOptional model reasoning-effort hint where supported.
append_previous_outputnoyes/no (default no). When yes, earlier dimension responses are included as context for later dimensions.
multiple_experimentsnoyes/no. When yes, the paper text is narrowed to one experiment.
experiment_number, experiment_textnoIdentify the target experiment when multiple_experiments=yes.

Comparison-type endpoints

These dedicated endpoints take the same fields and are equivalent to POST /compare with the matching mode:

  • POST /general_preregistration — requires preregistration + paper.
  • POST /clinical_trials — requires registration_id + paper.
  • POST /animals_trials — preclinical/animal registrations: registration_id + paper + an optional registration_csv file.

The dimensions_data field

A JSON-encoded array of objects, each with a dimension name and an optional definition. Order is preserved. At least one dimension is required.

[
  { "dimension": "Sample size", "definition": "The planned or realised number of participants…" },
  { "dimension": "Hypotheses", "definition": "The specific, directional predictions stated before data collection…" }
]

Example

curl -i -X POST https://<host>/compare \
  -F "client=openai" \
  -F "parser_choice=grobid" \
  -F 'dimensions_data=[{"dimension":"Sample size","definition":""}]' \
  -F "preregistration=@prereg.pdf" \
  -F "paper=@paper.pdf"

# → HTTP/1.1 302 Found
# → Location: /survey/<task_id>

3) Poll task status

GET /task_status/<task_id>

Returns the current state as JSON. Poll every few seconds until state is terminal.

{
  "state": "SUCCESS",                  // PENDING | IN_PROGRESS | SUCCESS | FAILURE | UNKNOWN
  "status": "Complete",                // human-readable progress message
  "processed_dimensions": 5,
  "total_dimensions": 5,
  "evidence_available": true,          // whether highlightable evidence artifacts exist
  "evidence_status": "ready",
  "result": {
    "items": [
      {
        "dimension": "Sample size",
        "deviation_judgement": "yes",  // "yes" | "no" | "missing"
        "deviation_information": "…",
        "registration_content_summary": "…",
        "paper_content_summary": "…",
        "registration_content_quotes": "[PREREG_0001, relevance_score=0.94] …",
        "paper_content_quotes": "[PAPER_0001, relevance_score=0.93] …"
      }
    ]
  }
}

Each quote string carries chunk IDs (e.g. PREREG_0001, PAPER_0001) and a cosine-similarity score; these IDs key into the evidence manifest below.

4) Retrieve the report

  • GET /result/<task_id> — the full interactive HTML report.
  • GET /report/<task_id>/manifest — JSON manifest of source documents and retrieved chunks (IDs, text, page/character locations).
  • GET /report/<task_id>/sources/<source_id>/render-data — the rendered text (and page offsets) for a source document.
  • GET /report/<task_id>/sources/<source_id>/pages/<n>.png — a rendered PDF page image (PDF sources only).
  • GET /report/<task_id>/sources/<source_id>/raw — the raw uploaded source, where available.

5) Notes & limits

  • Processing is asynchronous and depends on a running worker, a Redis instance, and the selected model provider being configured. If evidence_available is false after SUCCESS, the report still renders but without in-document highlighting.
  • Reports are addressable by an unguessable task_id link and persist until deletion is requested (see the Privacy Policy).
  • The API surface tracks the web app and may change. For source and issues, see the project on GitHub.
